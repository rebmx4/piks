# Проверка первого быстрого свайпа в APIKS

Владелец подтвердил: в установленной сборке `1790690505` первый быстрый
горизонтальный свайп по пустому месту после ножниц, выделения или ромбика
может не двигать ленту. В Safari на том же iPhone проблема не воспроизводится.
Это локализует различие в среде приложения, но не доказывает причину внутри UIKit.

Исходная рабочая оболочка: `720ad82`, `D:/Projects/piks`. Новый вариант — ветка
`fix/native-input-20261007`, отдельная рабочая копия на D:. Существующее приложение
`com.piks.app`, Apple ID `6794464999`; проект, инструменты и веб-редактор остаются прежними.

Одна проверяемая гипотеза: отдельный жест скрытого меню трёх пальцев может
задерживать завершение касания. Ему явно выставлены `delaysTouchesBegan = false`
и `delaysTouchesEnded = false`; число пальцев, длительность и меню сохранены.
Это тестовый вариант, а не подтверждённое устранение пропуска.

В TestFlight/Debug добавлен `InputTraceRecognizer`: он не распознаёт жест,
не отменяет и не задерживает касания, не препятствует другим распознавателям.
Он пишет начало/конец/отмену UIKit, физические координаты, время, число движений,
сдвиг, задержку доставки и состояния меню/прокрутки. На каждом движении сообщений
и обращений к JavaScript нет. Предел — 60 начал в минуту с явной записью лимита.
Запись только на текущем URL `/ryn-next/`, в веб-редакторе приёмник фильтрует
видимый экран. Приёмник `window.__ryndiInputTrace` подготовлен в Ryndi на ветке
`fix/native-input-diagnostics-20261007`; старая оболочка его не вызывает.

Рекомендации Apple: [задержка завершения касания](https://developer.apple.com/documentation/uikit/uigesturerecognizer/delaystouchesended),
[подкласс распознавателя](https://developer.apple.com/documentation/uikit/implementing-a-custom-gesture-recognizer).

Проверено локально: синтаксический разбор двух Swift-файлов tree-sitter-swift 0.7.4;
приём и полная запись сообщения UIKit без перемещения/выделения/отмены в браузерном
сценарии Chrome и WebKit; две проверки передачи полного сообщения через logqueue.
Сценарий сначала падал: приёмника сообщения UIKit в исходном варианте нет.

Первый вариант был собран в Codemagic №25 (`3071b27`, сборка `1791322272`),
загружен в существующее приложение TestFlight и установлен владельцем.
`menuDelaysEnd=false` подтверждено журналом, но пропуск сохранился.
На Windows нет Xcode; каждый новый вариант требует отдельной компиляции iOS.
Автозапуск workflow по push остаётся отключённым. Перед новым тестом нужны
выкладка приёмника только в NEXT через deploy.py и одна явно разрешённая
владельцем сборка этой ветки в существующее приложение TestFlight.
Публикация в App Store и изменения `/ryn/` не входят в задачу.

После установки: ножницы → сразу свайп по пустому месту; затем то же после
ромбика и выделения. Если пропуск остался, сопоставить `stream: native` с pointer/touch
по координатам и времени. Запись UIKit без соответствующего потока страницы означает
потерю до JavaScript; наличие обоих потоков требует проверки состояния/отрисовки.
Отсутствие записи при превышении явно указанного лимита не доказывает потерю касания.

## Продолжение 07.10.2026: дочерняя цепочка и отмена

Владелец разрешил подготовить следующую диагностику словом «Делай».
В актуальном NEXT `f8ba0f5` журнал приложения содержит отмены UIKit и DOM с целью
`WKChildScrollView` / `menu-clip`. Состояние основного pan равно 0 и не показывает
распознаватели дочернего контейнера. Эти записи не подтверждают причину пропуска
горизонтального свайпа именно по canvas.

`InputTraceRecognizer` теперь добавляет `traceVersion=2`, `observedWall` и `route`:
до 10 view от цели UITouch вверх по иерархии, до 24 распознавателей, явные признаки
усечения. Для каждого view — тип, ID в пределах процесса, прямоугольник в точках
WebView, видимость; для UIScrollView — enabled/delay/cancel, panState, offset/size.
Для жестов — тип, ID, state, enabled, cancel, delayBegin/delayEnd и число касаний.

Снимки снимаются только при начале/конце/отмене. Одна дополнительная запись
`afterCancel` в следующем проходе main queue позволяет увидеть состояние после
отмены, когда текущий callback UIKit ещё не закончен. Слабая ссылка на цель не
удерживает view; отсутствие цели явно записывается. Лимит 60 начал/мин сохранён.
Никакие состояния/политики других распознавателей или прокрутчиков не меняются.

Обновлённый приёмник NEXT сохраняет фактическое время входа обработчика DOM
`handledWall` отдельно от метки события `wall`, а также их разницу `queue`.
Для нативного сообщения отдельно записывается `receivedWall`.
Короткий тест Chrome/WebKit проверил полную передачу снимка дочернего контейнера
и `afterCancel`, различение задержки 300 мс и отсутствие влияния на проект.
Синтаксис Swift проверяется локальным tree-sitter; это не компиляция Xcode
и не подтверждение устранения пропуска на телефоне.

## Исправление замеров после проверки сборки 26

Владелец установил `1791355329`. Сеанс `7drrdky87h` потерял 608 строк журнала;
девять доставленных окончаний UIKit не содержат исходный view. Причина пропуска
свайпа остаётся неизвестной. Владелец разрешил исправление словом «Делай».

`traceVersion=3`: слабая ссылка на исходный UIView сохраняется с начала до
окончания/отмены, поскольку `UITouch.view` может быть пустым к окончанию.
Снимок ограничен 10 view и 64 распознавателями с явными признаками усечения.
Лимит снижен до 40 начал/мин; за пределом отмечается `phase=limit`, обычные
касания продолжают обрабатываться. Это соответствует проверенному бюджету
существующего транспорта при расширенном снимке; 60 требуют девяти пакетов/мин.

Приёмник NEXT объединяет границы и сжимает JSON встроенным gzip. Проверены
полное восстановление данных, отсутствие потерь в серии, незавершённое касание
и отсутствие влияния на состояние редактора в Chrome/WebKit. Синтаксис Swift
прошёл tree-sitter. Компиляция UIKit выполняется одной новой разрешённой сборкой
этой ветки в Codemagic; результат поведения проверяется отдельно на iPhone.
